# TG proxy

Асинхронный MTProto-прокси для Telegram с поддержкой WebSocket, Fake-TLS, IPv4/IPv6 dual-stack и каскадного проксирования (upstream туннелирование).

Проект разработан для обхода региональных блокировок (РКН / DPI), маскировки трафика под легитимный HTTPS и решения проблемы блокировки медиаконтента (фото, видео, стикеры, голосовые сообщения).

## Требования к системе

- **ОС**: Linux (Debian 11/12/13, Ubuntu 20.04+, Alpine и др.)
- **Python**: 3.10 или новее
- **Библиотеки**: OpenSSL (`libssl.so.3` или `libcrypto.so.1.1` — присутствует по умолчанию в большинстве дистрибутивов)

## Функционал

1. **Обход блокировок Telegram**:
   Провайдеры и ТСПУ блокируют прямые IP-адреса датацентров Telegram и сигнатуры протокола MTProto. TG proxy маскирует соединения под обычный HTTPS (TLS Handshake) и использует веб-сокеты Telegram (`kws*.web.telegram.org`), неотличимые от посещения защищенного сайта. Для отправки текстовых сообщений достаточно локального сервера.

2. **Решение проблемы с загрузкой медиаконтента (Каскад Local → VPS)**:
   Медиа файлы часто не загружаются из-за точечных блокировок CDN Telegram.
TG proxy решает это через гибридную схему:
   - **Текстовые чаты (DC2)** обрабатываются напрямую локальным сервером (минимальный пинг, экономия трафика VPS).
   - **Медиафайлы (DC1, DC2m, DC3, DC4m, DC5)** прозрачно туннелируются через внешний VPS (например, по IPv6 или IPv4 через Fake-TLS туннель).

3. **Zero-Dependency (Нулевые зависимости)**:
   Никаких сторонних библиотек, `pip install` или тяжелых фреймворков. Используется исключительно стандартная библиотека Python (`asyncio`, `ssl`, `hashlib`, `socket`) и системный `libcrypto` (OpenSSL через `ctypes`) для аппаратного шифрования AES-256-CTR.

4. **Полная поддержка Dual-Stack (IPv4 + IPv6)**:
   Прокси может слушать одновременно `0.0.0.0` и `::`, позволяя клиентам подключаться по любому доступному протоколу.

## Возможности

- **Два режима работы клиентов**:
  - `dd` (стандартный MTProto с обфускацией);
  - `ee` (**Fake TLS**) — полная маскировка трафика под TLS-сессию популярного сайта (Cloudflare, Mail.ru, Google и т.д.) с верификацией подписи в `ClientHello`.
- **WebSocket туннелирование**: прямое подключение к веб-шлюзам Telegram по протоколу RFC 6455.
- **Пул соединений (WS Connection Pool)**: фоновый прогрев и поддержание постоянных соединений с датацентрами для мгновенного отклика при отправке сообщений.
- **Каскадирование (Upstream Chaining)**: возможность использовать удаленный TG proxy как шлюз для определенных DC или исключительно для медиапотоков.
- **Множество ключей на одном порту**: поддержка разных секретов и маскировочных доменов для разделения доступа между пользователями.
- **Защита от активного DPI-зондирования**: при обращении с неверным секретом входящий трафик прозрачно перенаправляется на настоящий сайт-домен маскировки.
- **Резервирование (TCP Fallback)**: автоматический переход на прямой TCP при сбоях WebSocket.
- **Поддержка всех DC Telegram**: основные DC 1–5 и тестовый DC 203.

## Архитектура и схема работы

### Одиночный режим (на VPS или локальном сервере)

```
Telegram Client ──(TCP / Fake-TLS)──► [ tg-proxy ] ──(WebSocket TLS)──► Telegram DC (kws*.web.telegram.org)
                                                           │
                                                           └──(TCP Fallback)─► Telegram DC (IP:443)
```

### Каскадный режим (Локальный сервер + VPS)

```
                       ┌── Текстовые чаты (DC2) ───────► WebSocket ───────► Telegram DC2
                       │
Telegram Client ──► [ Local tg-proxy ]
                       │
                       └── Медиа (DC1, DC2m, DC3...) ──► Fake-TLS (IPv6) ─► [ VPS tg-proxy ] ──► Telegram DC
```

## Приватность и безопасность

### Что видит владелец прокси:
- IP-адрес подключенного клиента;
- Время и объем переданного трафика;
- Идентификатор датацентра (DC2 — Европа/РФ, DC4 — Америка и т.д.).

### Чего владелец прокси НЕ видит:
- **Содержимое сообщений, медиафайлов и звонков** (Telegram использует сквозное шифрование MTProto, прокси управляет только внешним транспортным слоем обфускации);
- Номера телефонов, Telegram ID, имена и контакты;
- Названия каналов и чатов.

## Установка

### 1. Клонирование или копирование файлов

Скопируйте проект в каталог `/opt/tg-proxy/`:

```bash
mkdir -p /opt/tg-proxy
cp tg-proxy.py crypto.py fake_tls.py raw_ws.py config.ini /opt/tg-proxy/
chmod +x /opt/tg-proxy/tg-proxy.py
```

### 2. Установка системной службы (systemd)

Скопируйте юнит-файл и запустите службу:

```bash
cp /opt/tg-proxy/tg-proxy.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now tg-proxy
```

Проверка статуса:
```bash
systemctl status tg-proxy
journalctl -u tg-proxy -f
```

## Конфигурация (`config.ini`)

Файл конфигурации расположен в `/opt/tg-proxy/config.ini`.

### Пример 1. Автономный сервер (VPS)

Слушает все порты по протоколу IPv4:

```ini
[server]
ip = 0.0.0.0
verbose = false

[keys]
; Формат: id = порт:секрет[:домен_маскировки]
; Ключ без домена -> обычный MTProto (префикс dd)
1 = 9999:12345678123456781234567812345678

; Ключ с доменом -> Fake-TLS режим (префикс ee)
2 = 10001:12345678123456781234567812345678:cdnjs.cloudflare.com

[datacenters]
1 = 149.154.175.50
2 = 149.154.167.51
3 = 149.154.175.100
4 = 149.154.167.91
5 = 149.154.171.5
203 = 91.105.192.100
```

**Внимание:** Клиенты Telegram подключаются только по IPv4, а IPv6 нужен только для upstream (каскада).

### Пример 2. Локальный сервер с туннелированием на VPS

Текстовые сообщения уходят с локального сервера, а медиа ходит через внешний VPS. Связь между серверами по IPv4 или IPv6:

```ini
[server]
; Слушает оба протокола
ip = 0.0.0.0, ::
; Логирование отключено
verbose = false

[keys]
1 = 9999:12345678123456781234567812345678
2 = 10001:12345678123456781234567812345678

[datacenters]
1 = 149.154.167.220
2 = 149.154.167.220
3 = 149.154.167.220
4 = 149.154.167.220
5 = 149.154.167.220
203 = 149.154.167.220

[upstream]
; IPv4 или IPv6 адрес удаленного VPS с tg-proxy
host = aaaa:bbbb:cccc:dddd:eeee:ffff:aaaa
port = 4444
secret = 12345678123456781234567812345678
domain = cdnjs.cloudflare.com

; Датацентры, которые всегда направляются через VPS
dcs = 1,3,5,203

; Автоматически направлять все медиа-потоки (DC1, DC2m, DC3, DC4m, DC5) на VPS
media = true

; Использовать upstream, если локальный WebSocket не ответил
fallback = true
```

## Использование и CLI утилиты

Запуск и управление через командную строку:

```bash
# Показать ссылки подключения tg://proxy для добавления в Telegram
python3 tg-proxy.py -l

# Проверить связность со всеми датацентрами Telegram и upstream-сервером
python3 tg-proxy.py -t

# Запуск в интерактивном режиме с подробными логами
python3 tg-proxy.py -v

# Указать нестандартный путь к файлу конфигурации
python3 tg-proxy.py -c /path/to/custom_config.ini

# Сброс настроек и генерация новой конфигурации
python3 tg-proxy.py -r
```

### Форматы ссылок для Telegram

- **Обычный MTProto (dd-режим)**:
  `tg://proxy?server=IP_АДРЕС&port=4444&secret=dd12345678123456781234567812345678`
- **Fake-TLS MTProto (ee-режим)**:
  `tg://proxy?server=IP_АДРЕС&port=9999&secret=ee1234567812345678123456781234567863646e6a732e636c6f7564666c6172652e636f6d`
  *(секрет содержит шестнадцатеричный HEX маскировочного домена)*


## Структура проекта

```
tg-proxy/
├── tg-proxy.py         # Основной сервер, маршрутизация DC и upstream
├── raw_ws.py           # Асинхронный WebSocket клиент (RFC 6455)
├── crypto.py           # AES-256-CTR через системный OpenSSL (ctypes)
├── fake_tls.py         # Поддержка Fake-TLS (серверная и клиентская части)
├── wstest.py           # Утилита быстрой диагностики доступности веб-сокетов
├── config.ini.example-local  # Пример конфигурации локального сервера
├── config.ini.example-vps  # Пример конфигурации внешнего сервера
├── tg-proxy.service    # Systemd юнит для автозапуска службы
└── README.md           # Документация проекта
```

## Удаление службы

Если требуется полностью удалить прокси с сервера:

```bash
systemctl stop tg-proxy
systemctl disable tg-proxy
rm -f /etc/systemd/system/tg-proxy.service
systemctl daemon-reload
rm -rf /opt/tg-proxy
```
